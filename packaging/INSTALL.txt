INSTALL
==================================

This lets a wired controller act as PLAYER 1 on a jailbroken PS4 running GoldHEN,
in every screen: home, settings, sign-in and games. The decoder has layouts for
the Xbox 360, Xbox One/Series, DualSense/DualSense Edge, Switch PDP and Switch Pro
(057E:2009, report 0x30) formats, including clones that use them. It creates a
virtual DualShock 4, so it is a GoldHEN *payload*.

Only the configuration marked Confirmed below has been observed working on a
console. A decoder layout is not a console confirmation.

Files here:

    AnyController.elf     the payload (this is the one you need)
    COMPATIBILITY.md    per-result evidence table
    INSTALL.txt         this file


What you need
-------------

* A PS4 on firmware 11.00, 9.00 or 13.52 with GoldHEN v2.4b18.10 or newer already
  running. All three create the virtual pad through the direct API path (seen
  working in console logs: 11.00 by the author, 9.00 and 13.52 in tester logs);
  11.00 also has the confirmed callsite-patch fallback. Other firmware uses the
  same direct path but has not been seen working.
* A DS4 (or equivalent) to boot the console and start GoldHEN; it is optional
  afterwards.
* Your controller's USB receiver (or cable) in a PS4 USB port.
* FileZilla (or any FTP client) to copy one file over.


What works (evidence, not guesses)
----------------------------------

Confirmed:
    Manba One V2, Xbox 360/XInput mode, 2.4 GHz USB receiver.
    PS4 11.00, GoldHEN v2.4b18.10+ (exact build not logged).
    Virtual pad created and fed; player 1 on home, menus and in games.

Partial:
    Manba One V2, Switch Pro mode (057E:2009, report 0x30), 2.4 GHz receiver.
    PS4 11.00, same GoldHEN. Pad created and fed, Y-axis fixed, no output
    errors; physical face-button labels are still unconfirmed.

    GameSir T4 Cyclone Pro receiver, Switch Pro mode, PS4 9.00 (tester log).
    Pad created and fed through the direct path. Face buttons were crossed in
    the build that was tested; fixed since, not yet re-tested on a console.

    GameSir T4 Cyclone Pro receiver in its own Xbox mode (3537:1015), PS4 9.00
    (tester log). Opened and fed; a face-button workaround meant for the Manba
    was applied by mistake after a Switch session. Fixed since, not re-tested.

Seen working in a tester log:
    GameSir Nova Lite receiver, Xbox 360 mode (3537:1040), PS4 13.52. Pad
    created and fed; sticks, D-pad and LB/RB appear in the log. Face buttons
    and triggers were not pressed in that run.

Failing:
    DualSense 054C:0CE6 (PS4 9.00 and 10.01) and Logitech Dual Action
    046D:C216 (PS4 9.00). The controller opens but sends no data to the
    payload. The cause is not known yet. This build tries recovery steps and
    writes each one to the log; if you test one of these, please send
    /data/AnyController.log.

Unsupported:
    DualSense/Edge adaptive triggers, haptics, LEDs, mic mute, battery state and
    touchpad coordinates. The virtual pad is input-only, on every firmware.
    DS4/DS4-mode pads are left to the console's native driver.
    PS3 pads, the Xbox 360 wireless receiver, steering wheels, keyboards and mice.

Untested:
    DualSense Edge 054C:0DF2 basic input, Xbox One/Series GIP including 13.52
    (the one log showed no USB devices), 8BitDo Xbox/Switch/D-Input (the log
    sent as 8BitDo was another controller's), "GameSir 2", Generic HID pads
    other than the failing Logitech Dual Action (for example the F310), and
    Machenike G1 on 13.52 with the current build. Do not report these as
    working.

Step 1 - copy the payload
-------------------------

With FileZilla: connect to the console over FTP, open /data/payloads/ on the
console, and drag AnyController.elf into it.

With a command line (replace <PS4-IP> with the console's address):

    curl -T AnyController.elf ftp://<PS4-IP>/data/payloads/AnyController.elf


Step 2 - start it once
----------------------

On the console: GoldHEN -> Utilities -> Payloader LaunchPad -> run AnyController.elf.

A few seconds later the console behaves as if a DS4 had just been plugged in:
"Who's using this controller?" appears. Pick your user and press a button on the
controller to accept it. The pad is now player 1 everywhere.


Step 3 - make it automatic (optional)
-------------------------------------

In the LaunchPad, highlight AnyController.elf and press Square to add it to the
AutoRun queue. Or edit /data/GoldHEN/payloads.ini by hand and add this line
(keep every other line already there) so it starts by itself on every boot:

    [AutoRun]
    /data/payloads/AnyController.elf = 1


Touchpad click
--------------

A DualSense's own touchpad click passes straight through. On a controller with
no touchpad, the virtual DS4's touchpad CLICK is fired by an L3+R3 chord:
program a back button (e.g. M3) on the controller to an "L3+R3" macro, and one
press does it. A held L3+R3 also works. On an Xbox Series pad the Share button
maps to the DS4 Share button.


How to stop it
--------------

There is no stop button inside the payload. To stop it for good, reboot the
console. Turning the controller off removes the virtual pad (the console goes
back to normal) but the payload keeps running, ready if the pad comes back.


If something is wrong
---------------------

The payload writes a log to /data/AnyController.log on the console. Grab it over
FTP and read it; the project's README has the full guide. The most common issues:

* Nothing happens -> the file is not in /data/payloads/ or GoldHEN is too old.
* "vda: no callsite patch for firmware ..." -> the direct path did not create a
  device and this firmware has no known patch. Send the vda/AddDevice lines.
* "vda patch: ... not patching" -> the FW 11.00 fallback did not recognise the
  callsite, so it refused to touch the system library. Update / report it.
* No "Who's using this controller?" prompt -> the receiver may not be a known
  device; check the "usb:" lines and the AddDevice/klog lines in the log.
* "no supported controller found; USB bus now:" -> the lines under it are what
  the console sees. If your controller is not listed there, the console does not
  see it at all (try another port or cable).
* "klog reader did not echo our marker" or "gave up after 3 AddDevice attempts"
  -> the kernel log never named the new device. Close any other klog client and
  replug the controller to try again.
* "controller opens but sends no data" or "reports arrive but none decode" ->
  send the log; the lines just above show the controller's interfaces and the
  recovery steps that were tried.

Nothing here is permanent and nothing is written outside /data/.
